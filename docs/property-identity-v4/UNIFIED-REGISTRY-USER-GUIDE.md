# Единый Property Identity Registry — инструкция пользователя

Дата: 2026-07-26  
Статус: реализация развёрнута в dev 2026-07-26; rollout реестра намеренно оставлен `DISABLED` до авторизованной проверки обычной формы

## Что это такое

Property Identity Registry — единый реестр физических объектов всей платформы Fixer.guru / KVARTAL. Это не отдельная база агентства и не отдельный кабинет.

- Один физический объект имеет одну карточку `PropertyObject` и один идентификатор IREPN.
- Несколько агентств могут работать с тем же объектом через собственные права представления и коммерческие предложения.
- Web3-токен подтверждает происхождение записи реестра. Он не доказывает право собственности на недвижимость и не заменяет юридические документы.

## Что делает партнёр

1. Войдите в существующий кабинет партнёра.
2. Откройте обычную форму «Новый объект».
3. Заполните объект, включая официальный идентификатор (для России — кадастровый номер Росреестра).
4. Приложите документы, подтверждающие право представления, и подтвердите декларацию ответственности агентства.
5. Если корпоративный BSC-кошелёк организации ещё не подключён, подтвердите его контроль подписью challenge.
6. Нажмите обычную кнопку сохранения/публикации.

Отдельную заявку Property Identity создавать не нужно. Отдельной страницы реестра в партнёрском кабинете нет.

## Что делает система автоматически

При сохранении обычного объекта система:

1. проверяет официальный идентификатор в едином реестре;
2. если совпадения нет — создаёт один канонический объект и его IREPN identity;
3. если точное совпадение есть — не создаёт дубль, а добавляет право представления и offer текущего партнёра;
4. фиксирует документально подкреплённую декларацию агентства и её evidence hash;
5. связывает корпоративный кошелёк агентства с единственным токеном объекта;
6. показывает в карточке объекта IREPN ID, статус identity, on-chain права и offer;
7. создаёт активное разрешение для конкретной витрины и offer после успешной технической проверки и Web3 reconciliation.

Публикация является декларацией агентства о наличии права представления, подтверждённого приложенными документами. Платформа не выдаёт это право и не проводит ручное одобрение обычной публикации. Последующий аудит может перевести право в `DISPUTED`, `SUSPENDED` или `REVOKED` с обязательной причиной.

## Что делает владелец платформы

Откройте `platform-admin → Property Identity Registry`.

- Управляйте единым контрактом, платформенным signer, token-операциями и reconciliation.
- Контролируйте технические ошибки, дубли, споры, приостановки и инциденты.
- Проводите последующий аудит документов только как отдельную контрольную процедуру, не как очередь одобрения публикаций.
- Управляйте rollout по рынкам только после E2E проверки обычной формы.

Платформа не обрабатывает «заявку на создание объекта»: объект, декларацию права, offer и публикацию создаёт и исправляет партнёр. Владелец платформы управляет реестром и аудитом, но не становится стороной обычной сделки.

## Корпоративный кошелёк и Web3

1. Администратор партнёра подключает корпоративный BSC-кошелёк в своём кабинете.
2. API выдаёт одноразовый EIP-712 challenge, связанный с пользователем, организацией, сетью и сроком действия.
3. Партнёр подписывает challenge своим кошельком; закрытый ключ остаётся у партнёра.
4. При публикации платформа добавляет или обновляет on-chain право этого кошелька на представление единственного токена объекта.
5. Единственный платформенный кошелёк, привязанный к `office@integrayachtsuae.com`, подписывает операции контракта через выделенный backend signer.
6. Секрет платформенного signer хранится только в Google Secret Manager и не попадает в браузер, PostgreSQL или логи.
7. Публикация считается Web3-verified только при `IN_SYNC`.

Рабочая сеть реестра — BNB Smart Chain Mainnet, chain ID `56`. Mainnet-запись включается только после полного E2E и отдельного change ticket владельца платформы.

## Как проверить в dev после deployment

1. Убедитесь, что старая страница `/property-identity` возвращает в обычный кабинет.
2. Создайте объект через обычную форму с новым кадастровым номером — должна появиться одна карточка с IREPN ID.
3. Повторите тот же кадастровый номер из другого партнёрского агентства — новая физическая карточка появиться не должна; у второго партнёра должно появиться собственное право/offer.
4. Подключите корпоративные кошельки обоих агентств и проверьте, что оба связаны с одним tokenId через разные representation records.
5. Проверьте, что объект появился только на разрешённой витрине и используется offer этого партнёра.
6. Отправьте обращение по offer второго агентства и убедитесь, что его получил только ответственный брокер этого агентства.
7. Запустите reconciliation и проверьте все хеши, receipt, событие, block hash и finality.
8. Откройте `/verify/{IREPN-ID}` и проверьте статус и BscScan. Адрес недвижимости, документы, контакты и цена на этой странице отсутствуют.

## Безопасный порядок deployment

1. Cloud SQL backup.
2. Применить миграции — первая отключит ошибочный rollout.
3. Развернуть office-api и platform-api.
4. Развернуть partner-admin, kvartal-admin, platform-admin и web.
5. Выполнить E2E обычной формы при выключенном rollout.
6. Включить `NEW_SUBMISSIONS_ONLY` без publish gate.
7. Выполнить duplicate/rights/offer E2E.
8. Включить publish gate и проверить витрины.
9. Web3 активировать в Mainnet только после привязки платформенного и агентских кошельков, проверки точного байткода контракта и резервного копирования базы.

## Технические первичные источники

- BNB Chain network configuration: https://docs.bnbchain.org/bnb-smart-chain/developers/wallet-configuration/

## Полный запуск Web3

Web3 управляется только владельцем платформы на странице `platform-admin → Property Identity Registry → Web3`.

1. Один раз привяжите публичный адрес платформенного BSC-кошелька к аккаунту `office@integrayachtsuae.com`.
2. Поместите закрытый ключ в отдельный секрет Google Secret Manager; предоставьте доступ только выделенному signer service account.
3. Разверните утверждённую версию контракта через backend signer при выключенном пользовательском трафике Web3.
4. API проверяет deployment receipt, адрес, точные ABI/runtime-bytecode hashes, владельца контракта и поддерживаемые интерфейсы.
5. Каждое агентство самостоятельно подключает корпоративный кошелёк через `partner-admin`.
6. Создание нового объекта ставит `MINT` и agency-representation операцию; повторный объект ставит только новую agency-representation операцию.
7. Backend signer отправляет транзакцию, сохраняет настоящий receipt/event и ждёт заданное количество подтверждений.
8. Статус `IN_SYNC` появляется только после совпадения token state, representation state и всех публичных хешей.
